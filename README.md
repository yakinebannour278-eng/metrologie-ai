# AI Pipeline for Drift Prediction and Anomaly Detection in Metrological Measurement Instruments

Internship project (PFE 2026) — L'Épi d'Or — ISO/IEC 17025 compliant AI pipeline predicting
instrument drift and detecting anomalies from historical calibration/verification data (ILA
metrology records), exposed to an existing .NET backend via a FastAPI microservice.

## Design principles followed in this project

- **No hardcoded paths or filenames** — everything resolves through `config/config.yaml`
  and `src/utils/config.py`.
- **Traceability first** — every automated decision (dataset selection, quality-check
  exclusions) is logged, not just printed, per ISO/IEC 17025 auditability requirements.
- **Real data only in `data/processed`'s test split** — augmentation never touches the
  test set, avoiding data leakage.
- **Notebooks compute, they don't assert** — every table, figure and conclusion in a
  notebook is derived live from the loaded dataframe.

## Regression API & metrologist interface (Phase 3+)

**Scope of this phase — read before use.** Only the regression model (next-value drift
prediction) is implemented and served. Anomaly detection and classification are **not**
implemented yet, are not exposed by any endpoint, and are not referenced anywhere in the
UI. The production architecture will eventually route through SQL Server + a .NET
backend; this FastAPI service is the AI microservice that architecture will eventually
call — SQLite here is a **local-prototype convenience only**, not a production database.

```
METROLOGIST INTERFACE (Streamlit, frontend/app.py)
        │  HTTP
        ▼
FASTAPI (src/api/main.py)
        │
PREPROCESSING + REGRESSION  (single joblib Pipeline — imputer → scaler → Lasso)
        │
PREDICTION
        │
RESULT DISPLAY + local SQLite history (data/metrology_ai.db)
```

### Model artifact

Produced entirely by `notebooks/05_Regression_Model.ipynb` — nothing below was hand-built
or invented outside that notebook's own output:

| File | Contents |
|---|---|
| `models/regression_active_model.joblib` | The full scikit-learn `Pipeline` (`SimpleImputer` → `StandardScaler` → `HuberRegressor`), fit together — selected objectively from an 18-algorithm benchmark (see `reports/quality/full_algorithm_benchmark.csv`), never hardcoded. The API calls `pipeline.predict(df)` directly and never re-implements preprocessing. `config/config.yaml` (section `api`) is the single source of truth for which artifact is actually loaded. |
| `models/regression_active_model_card.json` | Raw model card exported by the notebook. |
| `models/metadata.json` | Consolidated metadata the API reads at startup (feature order, target, evaluation metrics, **and honestly-reported limitations** — see below). |

**⚠️ Important, documented finding (do not hide this from the metrologist):** under
`GroupKFold` cross-validation, a trivial "no drift" persistence baseline (predict next
value = current value) achieves a **lower MAE (1.95)** and **higher EMT-conformity
agreement (92.5%)** than the deployed Lasso model (MAE 4.98, conformity agreement
47.5%). This is a real result from the training notebook (§11), not a bug. The API's
`/model/info` endpoint and the Streamlit "About this model" panel surface this
prominently. The Lasso model is still what's served because it's the best-performing
*learned* model (used for explainability/quantile intervals in the notebook) — but the
UI must not overstate its reliability.

**Prediction unit:** not recorded anywhere in the source data (it's instrument-category
dependent). `models/metadata.json` marks it `UNKNOWN / REQUIRES CONFIRMATION` rather
than guessing a unit (e.g. °C) — confirm with a metrologist per instrument category
before displaying one.

### Input features — including a caveat you need to know

The model's 12 features (`models/metadata.json → feature_order`):

| Directly observable at a new measurement | Historical (computed from an instrument's past campaigns) |
|---|---|
| `EMT_basse`, `EMT_haute`, `min`, `max`, `consigne`, `valeur_reference` | `rolling_min_3`, `rolling_max_3`, `rolling_mean_3`, `rolling_median_3`, `moving_average_5`, `ewm_mean` |

The 6 historical features **cannot** be known by a metrologist just by taking one new
reading — they're rolling/lag statistics over the instrument's prior campaigns. Rather
than inventing simplified fields or silently dropping them, the API exposes:

```
GET /model/instruments/{instrument_id}/last-known-features
```

which looks up the instrument's most recent row already computed by
`04_Feature_Engineering_Selection.ipynb` (in `data/processed/ILA_features_selected.csv`)
and returns it as a **suggestion** the metrologist reviews/edits before submitting — the
Streamlit UI wires this up with a "📥 Load last known values" button.

### Running it

```bash
# 1. Install dependencies (adds SQLAlchemy/streamlit/pytest/httpx to the existing env)
pip install -r requirements.txt

# 2. Start the API (creates data/metrology_ai.db on first run)
uvicorn src.api.main:app --reload

# 3. In a second terminal, start the metrologist interface
streamlit run frontend/app.py
```

The API defaults to `http://127.0.0.1:8000`; the frontend reads this from the
`METROLOGY_API_URL` environment variable (falls back to that default).

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness + whether the model loaded successfully. |
| GET | `/model/info` | Model name/version, target, feature order, evaluation metrics, **known limitations**. |
| GET | `/model/instruments` | Instrument IDs known from the training dataset. |
| GET | `/model/instruments/{id}/last-known-features` | Historical-feature suggestion for that instrument (404 if unseen). |
| POST | `/predict` | Runs a prediction, persists it to local history, returns a neutral interpretation. |
| GET | `/history?instrument_id=&limit=` | Local prediction history (SQLite). |

`POST /predict` request/response shapes are defined in `src/api/schemas.py`
(`PredictionRequest` / `PredictionResponse`).

### Validation

Enforced in `src/api/schemas.py` (pydantic) and `src/api/utils/validation.py`:
`instrument_id` non-empty · `year` within `config.yaml`'s `plausibility` range ·
`EMT_basse < EMT_haute` · `min ≤ max` · all provided numeric fields finite. Fields the
training data itself often lacks (e.g. `consigne`, missing in ~34% of rows) are optional
and pass through the pipeline's own median imputer, exactly mirroring training-time
behaviour instead of inventing a stricter rule.

### Interpretation, not verdicts

Per the project's hard requirement, the API/UI never label a prediction "safe",
"critical", or "dangerous" — there is no scientifically validated threshold for this
model. The response always carries `status: "prediction_generated"` plus a neutral,
factual `interpretation` string, and both `/model/info` and the UI state plainly that
this is a decision-support tool that does not replace a metrologist's judgement or
constitute ISO/IEC 17025 conformity evidence on its own.

### Tests

```bash
pytest tests/ -v
```

Covers: `/health`, `/model/info` (real metadata, not placeholders), a valid prediction
end-to-end (including history persistence), a missing optional feature (imputer path),
missing `instrument_id`, out-of-range `year`, `EMT_basse ≥ EMT_haute`, `min > max`, and
an invalid numeric type. All 9 tests pass against the actual trained artifact.

### What's intentionally NOT here

- Anomaly detection, classification, alerting — not built, not planned for this phase.
- SQL Server / .NET integration — future architecture, out of scope; SQLite here is a
  local-only prototype store.
- Authentication — the future .NET backend owns this; no fake auth layer was added.
- Any invented prediction unit, drift threshold, or confidence score not produced by
  the training notebook.
